# Lady-lens workflow

Use Lady-lens MCP tools when they are available. What each tool does is in the generated list below; this part says when to use them.

- Prefer the graph tools over built-in file tools for indexed code. Fall back to built-in file tools only when Lady-lens is unavailable, the target is outside the indexed repository, or the graph has not been synced.
- Register a new checkout with `repo_add({ path, sync: true })`. Run `repo_sync` after branch changes or when a result reports `synced: false`; it re-reads only files whose size or mtime changed and reports `commitsSince`. `repo_sync({ branch: 'feature-x' })` indexes that branch into its own scope `branch:feature-x` without checking it out.
- One daemon serves many projects: if the MCP URL has no `?repo=<folder|id>`, pass `repo` on a tool call to target another registered project (registered with `repo_add` first).
- Run `diff_impact` before committing (or with `from: 'main'` before a pull request): it lists the functions you changed, who calls them and which have no test. An empty caller list with `unresolved` above zero is not proof that nobody calls the function.
- Run `branch_impact` before merging a bugfix into another branch. Callers are found by whole-word name match, so a common function name gives extra hits.
- `discussion_save` stores branch and commit with the discussion; `discussion_query` marks sources missing on the current branch ("niet op deze branch") and lists the local branches that still have them.

Do not invent graph edges or claim a file is indexed without checking the tool result.

## Tools

- `discussion_build(question, responses, sources?, key?)`: Build and shape a discussion record with frontmatter markdown and metadata without saving it.
- `discussion_save(question, responses, sources?, sessionId?, writeMarkdown?)`: Save an AI round or conversation as a Discussion node in the graph, linked to grounded code/docs/decisions.
- `discussion_edit(id?, key?, appendResponse?, addSources?, question?, sessionId?, writeMarkdown?)`: Edit or append to an existing discussion (add responses from Claude/personas, add source links, update text).
- `discussion_load(sessionId?, id?, key?)`: Load stored discussions from the graph (by session, or by specific id/key).
- `discussion_query(topic?, node?, sessionId?, limit?)`: Find discussions related to a code file, decision, symbol, or topic keyword.
- `read_chunk(chunkId?, path?, startLine?, endLine?)`: Read a file or exact AST chunk from the repository. Pass chunkId (e.g. "chunk:core/auth.js#authenticate") for exact function/class body; or path with optional startLine/endLine. Small files come back whole; big files return an outline.
- `grep(pattern, path?, offset?, ignoreCase?)`: Search the repository for a regular expression, optionally scoped to a path.
- `glob(pattern)`: List repository paths matching a glob pattern (supports * and **).
- `exports(file)`: Which names does this file export? Complete list from the project graph.
- `exists(file)`: Does this file exist in the project? If not, says where a file with the same name does exist.
- `definedIn(symbol)`: In which file(s) is this function/name defined or exported? Complete answer from the project graph.
- `health(file?, module?, limit?, hubs?, bridges?)`: Code health: which files no test reaches (also through index.js), exports no test names, import cycles, imports past a module index.js, large files, fan-in/out, hotspots (churn x size); on request hubs and bridges. Worst first; per file, per module or the whole repo.
- `functionView(symbol, maxSites?)`: What does this function do, who calls it, which tests use it, which stories name it? Definition with lines and purpose, callers, tests (with test names), stories, bound (`resolved`) and unbound (`unresolved`) call counts; for a class also its methods (`children`) and subclasses (`inheritors`); only this function, not the whole file.
- `diff_impact(from?, to?, limit?)`: What does my change touch? The functions a diff changes (default: the work not committed yet; or `from`..`to`, a branch from its merge-base) with per function its callers (file, lines), tests, bound and unbound call counts, complexity, and test gaps (changed functions no test names). Riskiest first.
- `folderView(folder)`: How does this folder work? Its parts (sub-folders and files) with their role and key exports, which part imports or calls which, who uses the folder from outside, what is not clean; a folder that only passes on a package also shows that package. `text` is the answer as a block.
- `importedBy(file)`: Which files import this file? Complete list from the import graph.
- `imports(file)`: Which files does this file import? Complete list from the import graph.
- `searchView(query, caseSensitive?, wholeWord?, isRegex?, kind?, include?, limit?)`: Interactive code search: search text or symbol with case sensitivity, whole word, regex, file kind filter, and file include glob. Returns grouped matches with classification (definition, call, test, doc, reference).
- `graph_query(sessionId?, node?, kind?, history?, query?, outgoing?, incoming?, path?, maxDepth?, limit?)`: Query the current session code and decision graph by node or text context. A code file node gets its consequences (importedBy, calledBy, tests) and risks in both modes; a one-hop answer lists imports before calls and says `total` and `truncated`. With kind "doc" and a file path, the documents that name the path come first (`mentions: "path"`, then "name"), each with the `lines` that name it.
- `repo_list()`: List all registered repositories in lady-lens (including shared databases and active branches).
- `repo_add(path, db?, branch?, sync?)`: Register a repository in lady-lens, optionally linking to a shared database and syncing.
- `repo_remove(repo)`: Unregister a repository from lady-lens by ID or path.
- `repo_sync(full?, branch?)`: Index/sync the repository graph incrementally (or full).
- `branch_diff(from, to)`: Compare two branches without checking them out: files (added, removed, modified, renamed) and functions (added, removed, modified, renamed) and changed import and call relations (`relations`) that `to` changes since its merge-base with `from`.
- `branch_impact(change, against)`: Impact of a change on another branch: functions that `change` (e.g. release) modified or removed since the merge-base, where `against` (e.g. a feature) still uses them (file and line), whether `against` also modifies them (overlap), shared files and text merge conflicts.
- `mendix_diff(from, to)`: Mendix model changes of a branch, read from git (no checkout, no mxcli; MPR v1 and v2): commits (date, author), changed files, and per changed document (page, microflow, nanoflow, entity...) its module, folders, name, type and change. For a modified document: every added, deleted or modified element (widget, activity, parameter, sequence flow) with what it does (`detail`) and each changed property path with before and after; a pointer to another element shows as that element. For a microflow or nanoflow: before and after graphs (nodes with summary, sequence flows with case values), each node and edge with its status. Needs Node 22.13+ (`lens node`).
- `cross_repo_search(query, repos?, wholeWord?, caseSensitive?, isRegex?, kind?, limit?)`: Search text or a symbol in several registered projects at once: every project, or only `repos`. Matches per project (file, line, definition/call/reference); names that are not registered come back in `unknown`.
- `commit_show(commit)`: What one commit changed, without checking anything out: author, date, subject, files (added, removed, modified, renamed) and functions (added, removed, modified) against its first parent. For a merge commit this is what the merge brought in.
- `function_history(file, name?, ref?, max?)`: Commits that added, modified or removed one function, newest first (hash, date, author, subject). Without `name`: every commit that touched the file. Name-based: a renamed function starts a new history.
- `config_grep(pattern, path?, offset?, ignoreCase?)`: Search only supported configuration and project files, including .csproj and reference-manager XML.
- `config_references(reference, package?, path?, ignoreCase?)`: Find which config files reference a package, project, or Siemens functional block by name.
- `config_update(path, content, expectedHash?)`: Replace one supported configuration file and refresh its graph facts. Use expectedHash to prevent lost updates.
